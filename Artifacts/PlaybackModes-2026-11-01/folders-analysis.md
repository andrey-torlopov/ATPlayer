# ATPlayer: режим «Плейлисты / Папки» и порядок плейлистов

Дата: 1 ноября 2026 года. Статус: анализ; папки и перестановка плейлистов не реализованы.

**Вывод:** перестановка плейлистов — небольшая доработка. Папки — самостоятельная задача средней сложности, главным образом из-за доступа к внешним файлам и связи нынешнего проигрывателя с сохранёнными плейлистами. Аудиодвижок менять целиком не требуется. Для первой версии стоит ограничиться просмотром выбранного дерева, воспроизведением файлов текущего каталога и ручным обновлением.

Ориентир для одного разработчика, знакомого с проектом: **4–8 часов на перестановку плейлистов; 42–68 часов на папки с проверкой на устройствах**. Это инженерная оценка по исходникам, а не измерение скорости разработки или обещание календарного срока. Технический прототип доступа к папкам должен уточнить диапазон до реализации всего интерфейса.

## Граница задачи

Пользователь запросил реализацию режимов воспроизведения и отдельно анализ папок. Повтор плейлиста, shuffle и режим одного трека реализуются параллельно главным агентом; этот документ не является разрешением на реализацию папок. Публикация сборки в App Store исключена текущим запросом.

Зафиксированная база анализа: коммит `36429b63a4b4f5ab70d6308fe6d81a1c5e2d0718`. Ссылки на исходники ниже привязаны к этому коммиту: локальные номера строк `ATPlayerViewModel.swift` могут измениться при добавлении режимов воспроизведения. Перед реализацией папок нужно сверить актуальную очередь и переиспользовать её правила.

## Предлагаемое поведение первой версии

Это проектные решения для последующей реализации, а не уже работающие возможности.

| Действие | Предлагаемый результат |
|---|---|
| Переключить «Плейлисты / Папки» над библиотекой | Меняется только область библиотеки. Плеер, трек и позиция продолжают работать |
| Открыть «Плейлисты» | Существующие операции остаются; добавляется «Изменить порядок» со списком и ручками перетаскивания |
| Переставить плейлисты | Порядок сохраняется сразу; выбранный трек определяется по ID и не перезапускается. Обычный последовательный обход использует новый порядок при следующем переходе |
| Нажать «Добавить папку» | Системный выбор каталога; приложение сохраняет доступ к выбранному корню |
| Открыть сохранённый корень | Показать непосредственные подпапки и поддерживаемые аудиофайлы; вложенные уровни загружать по мере открытия |
| Открыть подпапку | Перейти на следующий уровень с кнопкой назад и понятным путём; длинный путь сокращается визуально |
| Нажать аудиофайл | Начать воспроизведение и создать временную очередь аудиофайлов именно этого каталога в видимом порядке |
| Перейти в другую папку во время музыки | Просмотр не изменяет текущую очередь; новая очередь появляется только после явного запуска другого файла |
| Дойти до конца каталога | Без повтора остановиться; не переходить неожиданно в соседнюю папку или плейлисты |
| Повтор / shuffle в папках | Повторять или перемешивать текущую очередь каталога; режим одного трека использовать по тому же контракту, что в плейлистах |
| Файл удалён или доступ отозван | Понятное сообщение; предложить обновить список или выбрать корень повторно. Не зацикливать попытки |
| Удалить корень из приложения | Забыть сохранённую ссылку. Исходные папки и файлы не удаляются; если этот корень играет, остановить его очередь и освободить доступ |
| Экспортировать плейлисты | Существующий JSON без папок и их временных очередей. Сохранение порядка плейлистов в формате экспорта — отдельное расширение формата, здесь не предлагается |

Папки сначала, затем аудиофайлы; внутри групп — естественная сортировка имён, чтобы `2` располагалось перед `10`. Первая версия показывает названия файлов сразу. Чтение длительности и тегов — лениво, без открытия всех аудиофайлов ради первого экрана. Пустые папки видны; неподдерживаемые файлы скрыты. Символические ссылки на каталоги не обходятся автоматически: это исключает циклы и выход из выбранного дерева.

Не включать в первую версию управление файлами, переименование на диске, общий медиакаталог, синхронизацию, поиск по всему дереву, рекурсивную очередь всех подпапок и экспорт папок. Ручное «Обновить», повторный вход в каталог и возврат приложения на экран обновляют видимый список. Постоянное наблюдение за каждым узлом дерева не требуется.

Такой объём сохраняет идею простого локального плеера: папка становится ещё одним способом выбрать музыку. После реализации описание продукта придётся скорректировать: наличие папок уже нельзя использовать как отличие в пользу других плееров.

## Техническая схема

### 1. Порядок плейлистов

В `PlaylistStorageService` добавить аналог `setTrackOrder`, принимающий полный упорядоченный набор ID плейлистов. Проверять отсутствие пропущенных и повторных ID, присваивать последовательные `order`, сохранять одной операцией с существующим rollback. Во view model — преобразование `IndexSet` в новый порядок и обновление секций; в V1 — отдельный простой редактор списка по образцу `PlaylistEditorV1`.

У модели уже есть нужные поля, поэтому для этой части миграция данных не нужна. Нельзя использовать названия как идентификаторы: плейлисты могут называться одинаково. Во время импорта/несовпадения актуального списка операция должна безопасно отклоняться. Перестановка не должна сбрасывать проигрываемый файл или историю shuffle.

### 2. Отдельные корни, временное дерево

Предлагаемые типы: сохранённый `FolderSource` с UUID, названием, bookmark корня и порядком; временный `FolderEntry` для строки каталога; `FolderBrowserViewModel` для пути, загрузки, ошибок и отмены; небольшой `FolderAccessService` для доступа и чтения каталогов. Названия предварительные, объём не требует отдельного пакета или общей переработки приложения.

В базу сохраняются только выбранные корни. Полное дерево не дублируется в SwiftData: содержимое может измениться вне приложения. Узлы и текущая очередь живут в памяти, при повторном открытии каталог читается заново. Для устойчивого выбора внутри сессии ID нужно сопоставлять с корнем и идентичностью файла; абсолютный путь не даёт гарантии после перемещения. При невозможности восстановить файл допустимо явно предложить обновление/повторный выбор.

Apple позволяет выбрать каталог через document picker: доступ распространяется на его содержимое и подпапки, bookmark позволяет восстановить ссылку после запуска. Но доступ может быть отозван, поэтому bookmark не означает вечное разрешение. Перед чтением открывается security scope, после окончания использования закрывается; операции с внешним содержимым координируются. В iOS-примере Apple используется minimal bookmark. Это совпадает с нынешним приёмом приложения. [Apple: Providing access to directories](https://developer.apple.com/documentation/uikit/providing-access-to-directories?changes=l_5&language=objc).

### 3. Одна очередь для двух источников

Нужно отделить минимальные данные проигрываемого элемента от `@Model TrackItem`: идентификатор, отображаемое название, источник для разрешения URL и сведения для Now Playing. Плейлист превращает свои записи в такие элементы; каталог создаёт элементы без вставки в плейлист. Аудиосервис продолжает получать разрешённый URL.

Новая библиотечная вкладка не должна владеть аудиосервисом. Активная очередь и доступ к её текущему файлу остаются у общего владельца воспроизведения. Это сохраняет фон, экран блокировки, Live Activity, паузу, seek и эквалайзер при переходе между каталогами. Контекст очереди должен явно различать плейлист, обычный последовательный обход плейлистов и каталог.

Интеграцию проводить после текущей доработки repeat/shuffle: использовать общую логику переходов, а не вторую реализацию для папок. Обязательны отмена устаревшего запроса и проверка поколения очереди: медленная загрузка файла не должна возобновить старый трек после нового выбора или паузы. Эти защиты уже есть в исходной view model, их нужно сохранить при выделении общего пути.

### 4. Работа с внешними файлами

Нынешний `collectAudioFiles` объявлен в `@MainActor` view model. `Task.yield()` даёт другим задачам возможность исполниться, но синхронные `enumerator.nextObject()` и чтение свойств остаются потенциально блокирующими. Для нового браузера чтение каталога и координацию нужно выполнять вне главного потока и возвращать UI только готовые значения; загрузку отменять при уходе с уровня. Apple отдельно предупреждает о неопределённой задержке I/O для iCloud, File Provider, USB и SMB и рекомендует асинхронную координацию на фоновой очереди. [Apple: Improving performance and stability when accessing the file system](https://developer.apple.com/documentation/foundation/improving-performance-and-stability-when-accessing-the-file-system?language=objc).

Для проигрываемого файла security scope должен оставаться открытым до прекращения чтения аудиодвижком. Завершение короткой операции `NSFileCoordinator` и жизненный цикл `AVAudioFile` — разные вещи: один успешный координированный вызов не доказывает безопасность последующего длительного чтения. Сначала нужен небольшой прототип открытия, воспроизведения и внешнего перемещения/удаления файла. Не удерживать координированную операцию на всю длительность песни без проверки поведения в фоне.

Если для активного файла потребуется `NSFilePresenter`, отдельно реализовать его жизненный цикл. Apple требует снимать регистрацию при переходе приложения в фон и возвращать при выходе на передний план, чтобы не блокировать другие процессы. Это особенно важно здесь, поскольку музыка должна продолжать играть при заблокированном экране. [Apple: NSFilePresenter](https://developer.apple.com/documentation/foundation/nsfilepresenter?changes=l_5_8), [Apple: NSFileCoordinator](https://developer.apple.com/documentation/foundation/nsfilecoordinator?changes=_5_7&language=objc).

Текущий `downloadFromiCloud` использует ubiquitous-item API и опрос статуса iCloud. Это не доказательство готовности произвольного стороннего File Provider. В первой проверке нужны локальные каталоги и iCloud Drive; остальные источники считаются непроверенными до отдельного устройства/провайдера. Открытие папки не должно скачивать всё её аудио; выбранный облачный файл может потребовать сеть. Кэш для гарантированного офлайн-доступа — отдельная функция и в эту оценку не включён.

## Объём и оценка

Оценка предполагает одного разработчика, существующий аудиодвижок и доступные iPhone/iPad для проверки локальных папок и iCloud. Нет серверной части, изменений аудиокодеков, публикации и массового тестирования сторонних провайдеров. Диапазон включает реализацию, самопроверку и исправление ожидаемых интеграционных дефектов.

| Этап | Сложность | Инженерные часы |
|---|---|---:|
| Сохранение и редактор порядка плейлистов | Низкая | 4–8 |
| Контракт очереди папки и прототип внешнего доступа/фона | Средняя, уменьшает неопределённость | 6–10 |
| Сохранённые корни, bookmarks, восстановление доступа | Средняя | 6–10 |
| Переключатель, ленивый браузер, путь и состояния списка | Средняя | 8–12 |
| Общий путь воспроизведения, repeat/shuffle, системные команды | Средняя–высокая | 10–16 |
| Ошибки, отмена, обновление базы и проверки iPhone/iPad | Средняя–высокая | 12–20 |

Расчёт выполнен Python; один инженерный день принят равным 8 часам. Полные формулы:

```text
Папки, минимум: (6 + 6 + 8 + 10 + 12) ч / (8 ч/день) = 42/8 = 5.25 дня
Папки, максимум: (10 + 10 + 12 + 16 + 20) ч / (8 ч/день) = 68/8 = 8.5 дня
Всё, минимум: (4 + 42) ч / (8 ч/день) = 46/8 = 5.75 дня
Всё, максимум: (8 + 68) ч / (8 ч/день) = 76/8 = 9.5 дня
```

Вывод вычисления:

```text
folders: 42–68 hours; (42/8)–(68/8) = 5.25–8.5 engineering days
all: 46–76 hours; (46/8)–(76/8) = 5.75–9.5 engineering days
```

Практический ориентир — **примерно 6–10 инженерных дней на обе части**, с уточнением после прототипа. Поддержка конкретного проблемного провайдера, постоянное наблюдение за деревом, рекурсивная очередь всех подпапок или гарантированный офлайн-кэш расширят объём; они не спрятаны внутри оценки.

## Порядок выполнения и критерии приёмки

1. **Сначала перестановка плейлистов.** Проверить сохранение после перезапуска, одинаковые имена, начало/конец списка, отказ сохранения, импорт и изменение порядка во время музыки. Текущий трек и позиция сохраняются. Обычная очередь учитывает новый порядок; повтор активного плейлиста и shuffle не уходят в другой плейлист.
2. **Затем прототип доступа.** Выбрать локальный корень и iCloud-корень, открыть вложенный файл, перезапустить приложение, воспроизвести в фоне, отозвать доступ и удалить/переместить файл извне. По результату зафиксировать жизненный цикл scope/coordinator/audio file. Если здесь обнаружится ограничение провайдера, уточнить поведение до полного UI.
3. **Добавить корни и браузер.** Проверить пустые папки, глубокий путь, одинаковые имена на разных уровнях, Unicode, большое число элементов, скрытые файлы, неподдерживаемые форматы, отсутствие обхода ссылочных циклов. Уход с уровня отменяет загрузку; старый результат не заменяет новый список. Видимый список обновляется по команде.
